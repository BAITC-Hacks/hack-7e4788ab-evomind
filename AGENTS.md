# AGENTS.md — HackAlem AI, команда evomind

Действует для всех трёх Codex-инстансов, каждый на своей машине:
**Coordinator** (Agent №1, Mac) и два **Worker Agents** (Agent №2, Agent №3,
Windows). Копируется в корень официального репозитория первым коммитом
после официального старта соревновательной части.

## Модель ролей

Роли Worker Agents **не назначены заранее**. До получения реального ТЗ
неизвестно, какая комбинация ролей понадобится — Backend+Frontend, AI/ML+
Frontend, Data+Visualization, Computer Vision+Application и т.п. Решение
принимает Coordinator сразу после анализа ТЗ и фиксирует в `TEAM_PLAN.md`
(шаблон — `templates/TEAM_PLAN.template.md`).

### Coordinator (Agent №1, Mac) — постоянная роль

1. Получает полное ТЗ после 13:00, читает его и отдельно критерии оценки.
2. За **первые 10-15 минут** (не 30-40!) определяет: обязательный результат,
   основной demo-flow, минимальный MVP на 5 часов, минимально необходимую
   архитектуру.
3. Решает, какие две рабочие роли оптимальны для этой конкретной задачи, и
   назначает их Agent №2 и Agent №3.
4. Фиксирует всё это в `TEAM_PLAN.md` — коротко, не как спецификация.
5. Создаёт GitHub Issues и распределяет их между `agent-2` и `agent-3`. Каждая
   Issue обязательно содержит **Acceptance Criteria / How to verify** —
   не только что сделать, но и как доказать, что это работает.
6. Запускает обоих Worker Agents параллельно как можно раньше.
7. Следит за зависимостями, ревьюит и мержит PR, разруливает интеграцию,
   ведёт почасовые checkpoint (`checklist/HOUR_CHECKPOINTS.md`).
8. После завершения важной задачи может создать **verification Issue** для
   другого Worker — перекрёстная проверка критичных мест (см. ниже).
9. Вправе перераспределять **ещё не начатые** Issues между Agent №2 и Agent №3,
   если распределение оказалось неэффективным. Начатую задачу без веской
   причины не передавать. Если один Worker освободился раньше — не оставляет
   его без дела, а переключает на testing/integration/documentation или
   новую роль.
10. Отвечает за README и итоговый запуск проекта к 18:00.
11. На финальном этапе (~code freeze) сам переходит в роль
    **Release / Integration** (см. раздел "Финальный этап").

### Worker Agent №2 и Worker Agent №3 (Windows) — универсальные роли

- Конкретная роль и границы ответственности определяются Coordinator в
  `TEAM_PLAN.md` после анализа ТЗ — не раньше.
- Берёт только Issues со своим лейблом-владельцем (`agent-2` или `agent-3`).
  Тематические лейблы (`frontend`, `ai`, `data`, `infra` и т.п.) Coordinator
  может добавлять дополнительно — они не меняют владельца задачи.
- Работает в длинной ветке `agent-2`/`agent-3`, каждую задачу — в подветке
  `agent-2-issue-<N>-slug` / `agent-3-issue-<N>-slug`.
- Коммитит и пушит прогресс не реже раза в час.
- **Перед открытием PR обязан сам**:
  1. запустить относящиеся к его части тесты;
  2. проверить build/typecheck/lint, если применимо в стеке;
  3. самостоятельно пройти основной сценарий своей функции руками (или
     скриптом), убедиться, что описанный в Issue "How to verify" реально
     воспроизводится.
  Только после этого — PR.
- Не трогает Issues и ветку другого Worker Agent.
- Если для своей задачи нужен контракт/изменение в зоне другого агента —
  не лезет туда сам, а сообщает Coordinator.
- Если Coordinator назначил **verification Issue** на чужую задачу —
  выступает как интегратор: запускает, проходит сценарий, проверяет
  контракт, ошибки, edge cases. Код автора без необходимости не переписывает.
  Найденные проблемы оформляет как отдельные Issues.

## Перекрёстная проверка

Не на каждую мелочь — только на критический demo-flow и точки интеграции
между агентами. После того как Worker закрыл важную Issue, Coordinator может
создать Issue вида:

> Проверь #12 как интегратор: запусти, пройди сценарий, проверь контракт,
> ошибки и edge cases. Код автора без необходимости не переписывать.
> Найденные проблемы — отдельными Issues.

...и назначить её другому Worker (лейбл — тот, кто проверяет).

## Финальный этап (примерно с code freeze, ~17:20)

Роли временно меняются:

- **Agent №2 → QA / Technical Verification.** Проверяет: запуск,
  API/AI/data-часть, обработку ошибок, тесты, критические edge cases.
- **Agent №3 → Demo / UX Verification.** Проверяет: основной пользовательский
  сценарий, интерфейс, loading/error states, демо-прогон, очевидные
  визуальные проблемы.
- **Coordinator → Release / Integration.** Проверяет: все PR смержены, main
  собирается, README актуален, env-переменные описаны, сторонние компоненты
  раскрыты, проект запускается с чистого состояния, основной demo-flow
  работает, в репозитории виден подтверждаемый прогресс.

## Compliance-раздел (обязателен к соблюдению всеми тремя агентами)

Эти правила — прямое следствие Положения о HackAlem AI (пп. 5.1.7, 5.4.4–5.4.16,
5.6, 5.9). Нарушение любого из них создаёт риск дисквалификации команды.

1. **AI-агенты разрешены.** Использование Codex и любых AI-инструментов для
   разработки не является нарушением само по себе (п. 5.4.12).
2. **Основная функциональность создаётся только после официального старта**
   соревновательной части (13:00, 23.09.2026). До этого момента в репозитории
   не должно появляться конкурсного функционала.
3. **Основная разработка — только в этом официальном репозитории.** Сторонние
   закрытые репозитории для хранения или разработки кода проекта запрещены
   (п. 5.4.9, 5.4.11, основание дисквалификации по п. 5.9.2).
4. **Сторонние компоненты обязательно раскрываются**: open-source библиотеки,
   модели, датасеты, шаблоны — указывать в README и/или коммитах (п. 5.4.4–5.4.6).
   Использование open-source само по себе не нарушение; нарушение —
   присвоение чужой существенной работы без указания источника.
5. **Каждый час соревновательной части должен существовать подтверждаемый
   промежуточный результат** в репозитории: код, функционал, прототип, схема,
   настроенная модель, тест, данные и т.п. (п. 5.4.8; отсутствие — прямое
   основание дисквалификации по п. 5.9.2).
6. **Важные изменения регулярно пушатся** — не копить локальные незапушенные
   коммиты дольше ~30-40 минут.
7. **Проект должен быть воспроизводимо запускаем** экспертами самостоятельно,
   без личных аккаунтов участников: если используются внешние сервисы/API —
   обязательны демо/тестовые доступы (п. 5.6.6).
8. **README обязателен** и должен содержать: описание решения, архитектуру,
   технологии, установку, запуск, зависимости, переменные окружения, порядок
   проверки основного сценария (п. 5.4.15, 5.6.4). Шаблон — в
   `templates/README.template.md`.
9. **После внутреннего code freeze (~17:20) не начинаем крупные новые функции** —
   только интеграция, багфиксы, README, финальная проверка (см. "Финальный этап").
10. **К 18:00 итоговая версия должна быть зафиксирована** в этом репозитории —
    именно это состояние будет оцениваться (п. 5.4.13–5.4.14). Изменения после
    18:00 не учитываются.
11. **Если агент не уверен, разрешено ли действие правилами Хакатона —
    он останавливается и спрашивает человека**, а не действует по своей
    интерпретации. Это касается в первую очередь: работы вне репозитория,
    использования сторонних сервисов, вопросов раскрытия источников.

## Ветки, роли, Issues

См. `TEAM_PLAN.md` (создаётся Coordinator после анализа ТЗ) и
`workflow/ISSUE_WORKFLOW.md` — полный процесс.

Коротко: `main` — интеграционная ветка Coordinator; `agent-2` и `agent-3` —
рабочие ветки Worker Agents (роль каждого определена в TEAM_PLAN.md);
подветки на каждую Issue (`agent-2-issue-N-slug`, дефис, не слэш — иначе
конфликт имён веток в git); PR из подветки в `main`, ревью и мерж —
Coordinator.

## Три разные машины

Coordinator работает на Mac, Worker Agents — на Windows-ноутбуках. У каждого
своя обычная копия репозитория (`git clone`), никаких worktree — три разные
физические машины уже дают нужную изоляцию. Инструменты по платформам:
`scripts/mac/` (bash, для Coordinator) и `scripts/windows/` (PowerShell, для
Worker Agents).
