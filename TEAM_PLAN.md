# TEAM_PLAN — EvoMind

## Цель и demo-flow

За 5 часов собрать воспроизводимый веб-MVP: представитель бизнеса вводит слабое
описание, получает минимум три уместных уточняющих вопроса, редактирует карточку
и видит рост прозрачного рейтинга; после подтверждения задача появляется в общем
каталоге, студенческая команда отправляет предложение, а бизнес вручную принимает
или отклоняет его.

## MVP

- Конструктор: свободный ввод, анализ полноты, минимум 3 вопроса, ответы,
  редактируемая карточка и ручное подтверждение.
- Карточка: название, контекст, потребность, пользователи, данные, ограничения,
  ожидаемый результат, критерии успеха, контакт и формат взаимодействия.
- Рейтинг 0–100: разбивка по семи критериям из ТЗ, уровень готовности, список
  улучшений и пересчёт только по подтверждённым данным.
- Каталог: все опубликованные задачи, сортировка по рейтингу, фильтры по теме и
  уровню готовности; низкий рейтинг не скрывает задачу.
- Отклики: идея, план, срок и ссылка на прототип; ручное принятие или отклонение
  бизнесом, без автоматического назначения.
- Минимум 5 синтетических карточек, 5 команд и 5 откликов для демонстрации.
- AI-функция анализирует пробелы и формирует вопросы/черновик карточки. При
  недоступности API работает детерминированная заглушка; пользователь всегда
  редактирует и подтверждает результат, новые факты не придумываются.

Не входят в MVP: регистрация, сложные роли, чат, уведомления, файлы, календарь,
собственная ML-модель, векторная БД, production-инфраструктура и мобильная версия.

## Архитектура

Монорепозиторий с веб-клиентом и API. Предпочтительный стек для быстрого MVP:
React + TypeScript + Vite на клиенте, Node.js + TypeScript + Express на сервере,
SQLite для локально воспроизводимых данных. Общие TypeScript-типы и схемы
валидации находятся в `shared/`. Конкретные пакеты разрешено скорректировать до
начала реализации, если это ускоряет команду, но публичные контракты ниже должны
сохраниться.

Основные модули:

- `client/`: конструктор, редактор карточки, рейтинг, каталог, форма отклика и
  экран решений бизнеса.
- `server/`: REST API, хранение, рейтинг, AI-адаптер, каталог и отклики.
- `shared/`: DTO, enum статусов и схемы валидации.
- `seed/`: синтетические данные и один стабильный демонстрационный сценарий.

## Роли и границы

### Agent №2 — Backend / AI / Data

Владеет `server/`, серверными тестами, БД/seed и доменными функциями в `shared/`.
Реализует модель данных, формулу рейтинга, уровни готовности, AI-адаптер с
fallback, REST API, сортировку/фильтрацию каталога, отклики и ручные решения.
Не меняет UI Agent №3 без согласования. Любое изменение опубликованного DTO
сначала фиксирует в Issue/PR и сообщает Coordinator.

### Agent №3 — Frontend / UX / Demo

Владеет `client/`, UI-тестами и сценарием демонстрации. Реализует сквозной UX:
черновик → вопросы → редактирование → рейтинг → публикация → каталог → отклик →
решение бизнеса, включая loading/empty/error states. Работает с API только через
контракты `shared/`; не дублирует формулу рейтинга и не меняет серверную модель без
согласования.

### Coordinator — Integration / Release

Владеет интеграцией, ревью и merge, общей конфигурацией, README, почасовыми
checkpoint, проверкой контрактов и финальным demo-flow. Разрешает конфликтующие
изменения и после code freeze координирует только интеграцию, багфиксы и сдачу.

## Контракты между частями

Канонический формат ошибки: `{ "error": { "code": string, "message": string,
"details"?: unknown } }`. Все даты — ISO 8601, идентификаторы — строки. API не
возвращает факты, отсутствующие во вводе пользователя.

Ключевые DTO:

- `TaskCard`: `id`, `status` (`draft|published`), `title`, `context`, `need`,
  `users`, `data`, `constraints`, `expectedResult`, `successCriteria`, `contact`,
  `interactionFormat`, `topic`, `score`, `readinessLevel`, `scoreBreakdown`,
  `missingFields`.
- `ClarificationResult`: `questions` (минимум 3), `suggestedCard`, `mode`
  (`ai|fallback`), `warnings`.
- `Proposal`: `id`, `taskId`, `teamId`, `solutionIdea`, `plan`, `timeline`,
  `prototypeUrl`, `status` (`pending|accepted|rejected`).

Минимальные endpoints:

- `POST /api/tasks/analyze` — текст/известные поля → вопросы и черновик карточки.
- `POST /api/tasks` и `PATCH /api/tasks/:id` — создать/редактировать черновик и
  вернуть пересчитанный рейтинг.
- `POST /api/tasks/:id/publish` — ручное подтверждение и публикация.
- `GET /api/tasks?topic=&readiness=&sort=score_desc` — открытый каталог.
- `POST /api/tasks/:id/proposals` — отправить отклик.
- `GET /api/tasks/:id/proposals` — предложения для сравнения.
- `PATCH /api/proposals/:id/status` — ручное `accepted|rejected`; несколько
  предложений могут быть приняты, автоматический выбор запрещён.

Формула рейтинга является серверной и детерминированной: контекст + потребность
20, данные 20, ожидаемый результат 15, критерии успеха 15, ограничения 10,
пользователи 10, связь с бизнесом 10. Уровни: `draft` 0–39, `workable` 40–69,
`ready` 70–89, `priority` 90–100.

## Порядок интеграции

1. Coordinator утверждает DTO и создаёт первые Issues.
2. Agent №2 поднимает API/seed и публикует примеры запросов/ответов.
3. Agent №3 параллельно строит UI на fixtures, совпадающих с DTO.
4. После первого PR соединяем UI с API и проверяем основной сценарий.
5. К code freeze: Agent №2 выполняет техническую проверку, Agent №3 — demo/UX,
   Coordinator — чистый запуск, README, интеграцию и итоговый merge.

## Definition of Done

Из чистого клона проект запускается по README; один подготовленный пример за
5 минут проходит весь обязательный сценарий; рейтинг и его изменение объяснимы;
AI/fallback показывает вход, структурированный выход и обработку ошибки; проверки
build/typecheck/test проходят; сторонние библиотеки, модели и данные раскрыты.
